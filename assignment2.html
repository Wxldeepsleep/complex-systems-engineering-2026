系统定义 System of Interest

面向高阶智能驾驶的线控底盘系统，是在传统底盘机械连接（转向柱、液压/真空制动、机械节气门）基础上，以“电信号传递控制指令、分布式执行器独立驱动”为核心，集成线控转向（SBW）、线控制动（BBW）、线控驱动（含电驱动/电油门协调）、悬架与车身姿态控制等子系统，并与智驾域控制器（ADC/ADU）、整车电子电气架构深度耦合的底盘执行层系统。

其本质是高阶智能驾驶（L2+ 至 L4 分级）的“最后一公里执行机构”：上层智驾算法给出纵向加减速、横向转角与车身稳定性目标，线控底盘将其实时、精确、安全地转化为车轮与路面的力与运动。

外部环境 / 互操作系统
  • 智驾域控制器（感知—决策）
  • 整车控制器 VCU、动力域
  • 高压电源与电池管理 BMS
  • 整车信息娱乐 / HMI 仪表
  • 车云后台、OTA 与诊断系统
线控底盘系统（SoI）
  • 线控转向子系统 SBW（转向执行、路感反馈、冗余）
  • 线控制动子系统 BBW（制动执行、驻车、冗余备份）
  • 线控驱动/协调子系统（扭矩响应、驱动防滑）
  • 悬架与姿态控制子系统（CDC/空气悬架协调）
  • 底盘域控制器（信号融合、整车动力学协调、冗余监控）
外部物理环境
  • 道路与路面附着条件（干/湿/滑/冰雪/颠簸）
  • 交通参与者与交通信号
  • 环境温度、振动、电磁干扰
  • 车辆载荷、轮胎状态与老化
边界说明：感知与决策算法（摄像头、雷达、规控模型）属于智驾域，不在本系统内部；本系统只对“控制指令的接收—解析—协调—执行—状态反馈”负责。制动/转向的机械备份与失效降级策略属于本系统必须考虑的运行与安全约束。

BRS · 业务需求规格说明

对应参考资料表 4-1《ISO/IEC/IEEE 29148:2018 标准中的 BRS 范例轮廓》，按其条款逐项展开。

1.1业务目的

在汽车智能化、电动化转型背景下，传统液压/机械底盘无法满足高阶智能驾驶对快速响应、精确可控、冗余安全与整车动力学协同的要求。企业启动线控底盘项目，目的是：

  • 支撑高阶智驾落地：为 L2+ 至 L4 级自动驾驶提供可由算法直接控制的转向、制动、驱动执行接口，使上层决策能够闭环控制车辆运动。
  • 提升产品竞争力与技术自主可控：掌握线控底盘核心执行与控制技术，缩小与国际标杆在底盘电动化、智能化上的差距，支撑新车型平台溢价。
  • 改善驾乘安全与体验：通过主动稳定、冗余备份与失效降级，降低事故风险；通过平顺、线性的执行响应提升舒适性与路感一致性。
1.2业务范围
  • 业务域：智能电动汽车底盘电动化与智能化，覆盖线控转向、线控制动、驱动协调、悬架姿态协调及底盘域控制。
  • 在范围内：底盘域控制器软硬件、各线控执行器及冗余单元、与智驾域/动力域/电源域的接口定义、台架与整车标定验证、量产装车与售后保障。
  • 范围以外：感知传感器、自动驾驶规控算法本体、车身内外饰、轮胎与整车总布置；上述由其他系统/部门负责，本系统通过接口与其协同。
1.3业务概况

底盘是连接“车辆决策”与“路面力/运动”的执行层。内部分块为转向、制动、驱动协调、悬架姿态四个执行子系统与一个底盘域控制器；外部与智驾域、动力域、电源域、HMI、车云/诊断系统交互。各子系统通过车载总线（CAN/CAN FD/车载以太网）交换信号与数据，由底盘域控制器完成动力学协调与安全监控。

1.4定义
  • 线控（X-by-Wire）：以电信号代替机械/液压硬连接传递控制指令，由独立布置的执行器完成转向、制动等动作。
  • SBW / BBW：线控转向 / 线控制动。
  • 冗余与降级：主通路失效后由备份通路维持基本可控；降级指在部分功能受限条件下保证安全行驶。
  • SoI：系统所关注对象，即本线控底盘系统。
1.5主要相关方

业务管理层面识别的主要相关方：整车制造企业（投资方/采办方）、智驾与整车研发团队、底盘供应商与执行器厂商、行业主管与法规标准机构、最终用户与车主；详细分类与清单见后文“相关方列表”。

3.1业务环境
  • 政策法规：智能网联汽车准入与上路管理日趋规范；功能安全、预期功能安全、信息安全与网络安全成为强制约束；线控转向/制动需满足法规对转向失效、制动失效的安全冗余要求。
  • 市场趋势：高阶智驾渗透率快速提升，用户对自动泊车、高速/城市领航、主动安全的接受度提高；竞品普遍布局线控底盘平台。
  • 技术基础：电动化提供了电机、高压电源与分布式电控基础；车载以太网、域集中架构为底盘集成提供条件；同时供应链在执行器、芯片、冗余件上存在自主可控压力。
  • 社会与责任：底盘直接关系行车安全，事故责任与品牌声誉高度相关；需考虑噪声、振动、电磁辐射对乘员与环境的影响。
3.2使命、目的与目标

系统通过接受上层智驾或驾驶员指令，实时生成并执行车辆纵向、横向及姿态控制，达成以下业务结果：

  • 使命：成为高阶智能驾驶可信赖的执行底座，保障车辆在各类道路与工况下可控、安全、平顺地行驶。
  • 目的：把决策层的运动目标稳定、精确地落到车轮与路面；在正常与失效工况下维持车辆可控。
  • 可衡量目标（业务级）：支撑车型达到既定智驾等级；关键执行响应与控制精度满足平台指标；量产装车并通过法规与安全认证；售后故障率与召回风险控制在企业质量目标内。
3.3业务模型
  • 产品形态：面向企业自有及合作车型平台，提供成套线控底盘系统（域控制器 + 转向/制动/驱动/悬架执行器）及标定、配套与售后。
  • 供应与合作：整车厂主导系统集成与定义；执行器、传感器、芯片等由一级供应商配套，关键件需有备选来源以保障供应链安全。
  • 盈利与价值模式：以平台化底盘方案支撑高端智驾车型销售溢价；通过后续 OTA、标定迭代与售后维护持续创造价值。
  • 地域分布：研发、标定与测试围绕整车研发布局，量产装配随整车制造基地落地，售后覆盖主要销售区域。
3.4信息环境
  • 项目组合：线控底盘需与同平台智驾项目、电子电气架构项目统筹优先级与接口，避免多项目重复定义接口。
  • 长期系统计划：域集中—中央计算架构演进路线作为设计约束，底盘域控制器需预留接口与算力冗余，支持向区域控制器演进。
  • 数据配置：统一底盘信号字典、标定数据与故障诊断数据的组织规则，明确数据可用性、可访问性与安全保密约束。
4.1业务过程

底盘支撑的核心业务活动按层次分解为：

  • P1 指令接收：接收来自智驾域（自动驾驶目标）或驾驶员（转向/制动/油门操作）的控制意图。
  • P2 协调决策：底盘域控制器融合各执行子系统状态、车辆动力学与路面附着条件，分配转向、制动、驱动与悬架控制量。
  • P3 执行输出：各线控执行器独立驱动车轮转向、制动减速、扭矩输出与姿态调节。
  • P4 状态反馈与监控：采集执行器状态、轮速/转角/压力等信号，回传整车与智驾域；持续监控安全与冗余状态。
  • P5 失效应对：检测主通路异常后切换备份通路或进入安全降级，并向仪表/后台告警。
4.2业务运营策略与规则
  • 控制优先级规则：安全相关操作优先于舒适性与节能优化；驾驶员应急操作在规则允许范围内优先于自动控制（具体接管策略由整车 HMI 与法规确定）。
  • 协调规则：纵向（加减速）与横向（转向）控制需结合附着条件协调分配，避免超出轮胎附着力极限。
  • 安全规则：任何控制输出必须经过状态监控与合理性校验；关键子系统必须具备冗余或降级路径。
4.3业务运行约束
  • 性能时序约束：控制指令须在整车动力学允许的时间窗内完成响应；关键安全链路时延满足平台与法规指标。
  • 环境约束：在规定温度、湿度、振动、电压范围与电磁环境内可靠工作；超出边界时按降级策略处理。
  • 可追溯约束：关键控制动作、故障事件与标定版本须被记录并可追溯，支持诊断与责任界定。
4.4业务运行质量
  • 可用性与可靠性：关键行驶功能可用率高，平均无故障时间达到企业质量目标；安全相关功能按功能安全等级设计。
  • 使用质量：在效能（按目标轨迹/车速完成控制）、效率（响应及时、能量利用合理）、满意度（平顺、路感自然）与使用风险（避免误动作、误告警）上满足平台体验要求。
4.5业务结构
  • 组织结构：整车厂下设底盘系统工程、智驾集成、标定测试、质量与售后部门；供应商侧设执行器研发、供货与现场技术支持团队。
  • 角色职责：系统工程师负责需求与架构；控制/硬件/软件工程师负责实现；标定与测试人员负责验证；售后负责维修与故障反馈。
  • 资源共享：台架、仿真环境、试验场地与诊断工具在项目与车型间共享复用。
5.1初步运行概念
  • 运营政策与约束：系统服务于整车高阶智驾与安全行驶目标；设计与运行须遵守法规、功能安全与信息安全约束。
  • 系统描述：以底盘域控制器为协调核心，线控转向、制动、驱动、悬架执行器分布式布置，接收指令并闭环控制车辆运动。
  • 运行模式：驾驶员手动模式、自动驾驶（领航/泊车等）模式、混合接管模式、冗余降级模式。
  • 用户类型与相关人员：驾驶员/车主、智驾系统（自动控制方）、售后维修人员、标定测试人员。
  • 支持环境：车载供电与总线环境、诊断与 OTA 后台、维修工具与备件体系。
5.2初步运行场景
  • 场景 S-01 高速领航巡航：智驾域给出车速与换道转向目标，底盘协调加速、转向与制动，保持车道与车距。
  • 场景 S-02 城市道路跟停与起步：在拥堵路况下完成纵向跟车、停车保持与平顺起步。
  • 场景 S-03 自动泊车：低速大转角转向与精确制动配合，完成泊入/泊出。
  • 场景 S-04 紧急避障与制动：触发主动安全时执行快速制动与稳定性控制。
  • 场景 S-05 主通路失效降级：某执行或电控通路异常时切换备份，维持安全可控并告警。
6其他初步生存周期概念
  • 采办：整车厂定义系统需求与平台指标，向执行器/控制器供应商采购配套件，通过定点、开发与验收流程集成。
  • 部署：随整车总装下线，完成控制器标定写入、总线配置与下线检测。

  • 技术成熟度：在给定时间窗内采用成熟度可控的技术与供应链方案，预留演进空间。

02

运营概念 ConOps（组织层面）

ConOps 在组织/体系层面描述企业预期如何运作、目的与目标，以及体系内各系统（整车、智驾、底盘、动力等）如何协同；是多对多的体系关系，而非单一系统内部设计。

目标、目的与期望

  • 目标：在企业智能电动汽车产品体系中，建成可复用的线控底盘平台，支撑多车型高阶智驾。
  • 目的：把车辆运动控制能力从“机械/液压执行”升级为“电信号驱动、可被算法闭环控制、具备冗余安全”的执行底座。
  • 期望：底盘与智驾、动力、电气架构协同演进；平台化复用降低后续车型开发成本；安全与体验达到同级标杆水平。

项目范围与相关方职责

  • 范围：线控底盘系统的定义、开发、集成、验证、装车与售后支持；不含感知决策算法与车身工程。
  • 职责划分：整车厂负责系统定义、集成与验收；底盘团队负责系统架构与控制策略；供应商负责配套件交付；法规机构监督准入安全；用户提出使用与体验诉求。

体系将如何运行 多对多协同

在整车体系中，交通环境与车辆状态由感知系统采集，智驾域完成决策并输出运动目标；线控底盘作为执行体系的一环，与动力域、电源域、车身系统协同完成车辆运动；整车状态与故障信息回传车云，支撑 OTA、诊断与质量改进。ConOps 关注的是这些系统组合如何共同支撑“安全、高效、舒适地把乘员从出发地送到目的地”这一业务使命，线控底盘只是其中可被独立定义的一个系统。

信号

转角、轮速、压力、姿态等传感信号与控制指令

数据

标定数据、故障码、车辆状态与版本信息

物质

制动液/储能件、执行器机械结构与连接件

能量

高压/低压电能转化为转向、制动、驱动机械能

活动

驾驶员操作、系统执行动作、维修与标定活动

ConOps 与 OpsCon 区分：ConOps 是组织/体系层面“领导想要如何运作业务”的全局意图；OpsCon 是随后在系统层面，针对线控底盘这一特定系统描述“它将做什么、为什么做”。

StRS · 相关方需求规格说明

对应参考资料表 4-5《ISO/IEC/IEEE 29148:2018 标准中的 StRS 范例轮廓》，从业务运行与相关方视角展开。

1.1相关方目的

各相关方希望通过该线控底盘系统：在安全可控前提下获得自动驾驶与主动安全能力；获得平顺、自然的驾乘体验；并使开发、制造、维护与监管活动具备清晰、可追溯、可验证的依据。

1.2相关方范围

覆盖系统全生存周期中的直接使用方、交互/使能系统所有方，以及施加影响或被影响的机构与个人；范围随采办、开发、部署、运行、支持、弃置各阶段展开。

1.3 / 1.4概况与定义

概况与术语沿用 BRS 第 1.3、1.4 条；StRS 在此基础上补充运行视角的相关方诉求与使用场景。

1.5相关方

完整相关方分类、利益点、态度、影响力与重要性分析见后文“相关方列表”章节。

2参考

同 BRS 第 2 条；另补充各相关方所在领域的企业标准、接口规范、维修手册模板与测试规范。

3.1–3.4业务管理需求（继承）

StRS 继承 BRS 中业务环境、使命目的与目标、业务模型与信息环境的约束，不重复展开；当相关方运行需求与业务目标冲突时，以业务安全目标与法规为最高优先级进行权衡。

4.1系统过程

从运行视角，底盘系统过程为：指令接收 → 状态采集 → 协调控制量分配 → 执行器驱动 → 反馈闭环 → 安全监控与降级。每个过程都需与上层智驾/驾驶员及下层执行器明确输入输出与接口。

4.2系统运行策略与规则
  • 控制输出须满足平顺性与稳定性约束，避免急打方向、突兀加减速。
  • 自动与手动控制之间的切换须平滑、可感知、可解释，避免控制交接抖动。
  • 故障诊断与告警规则须分级：提示、降级、停车安全处置逐级触发。
4.3系统运行约束
  • 工作环境、电压、温度、振动与电磁兼容范围约束；超出范围进入保护/降级。
  • 接口信号协议、报文格式与时序约束；与整车电气架构版本兼容。
  • 安全与信息安全约束：关键功能防误触发，通信与诊断具备访问控制与防护。
4.4系统运行模式与状态
  • 手动驾驶模式：驾驶员直接操作，底盘提供助力与稳定支持。
  • 自动驾驶模式：智驾域下发目标，底盘闭环执行转向、制动、驱动。
  • 接管/混合模式：人机权限过渡，双方指令按规则融合或切换。
  • 冗余降级模式：主通路失效后备份通路工作，功能受限但保持可控。
  • 驻车/下电状态：驻车制动保持、控制器休眠与唤醒管理。
5用户需求
  • 驾驶操控响应跟手、方向与制动反馈自然，无虚假路感与迟滞。
  • 自动驾驶下车辆沿目标轨迹平顺行驶，加减速与转向不突兀。
  • 系统状态与告警清晰可读，接管请求时机合理、方式明确。
  • 故障情况下车辆尽量维持可控，提示驾驶员采取安全措施。
04

运行概念 OpsCon（系统层面）

OpsCon 是面向用户/运营者的系统级文档，描述线控底盘“将做什么、为什么做”，包括上下文、运行环境、正常与退化运行场景及异常场景；用于派生后续系统需求，而非规定具体设计实现。

系统上下文与边界 导出接口需求

线控底盘向上对接智驾域与驾驶员输入，向下对接各线控执行器与传感器，对外通过总线/以太网交换信号与数据；上下文环境导出系统边界、外部接口与互操作系统清单。

正常与其他运行环境 导出环境需求

涵盖城市道路、高速公路、停车场、低附着路面、颠簸路面，以及冷热环境、高/低电压、正常与老化车辆载荷等条件；系统须在规定环境范围内保持性能，超出范围按降级策略保护。

运行阶段与活动分解 任务剖面

上电自检下电唤醒阶段
控制器与执行器上电，完成自检、状态读取与冗余通路确认；活动：节点初始化 → 故障自检 → 状态上报 → 就绪/不可用判定。
手动行驶驾驶员控制
响应方向盘、制动踏板与加速操作，提供转向助力、制动助力与稳定控制；活动：操作采集 → 助力/力分配 → 执行 → 路感反馈 → 稳定监控。
自动驾驶执行智驾控制
接收智驾域纵向/横向目标，协调转向、制动、驱动与悬架完成轨迹跟随；活动：目标解析 → 附着/状态融合 → 控制量分配 → 执行闭环 → 状态回传。
人机接管过渡混合模式
在自动与手动之间平滑交接，避免控制权突变；活动：接管请求提示 → 权限判定 → 指令融合/切换 → 平顺过渡确认。
失效降级退化运行
主通路异常时切换备份或进入受限运行，保证基本可控；活动：异常检测 → 冗余切换 → 降级限幅 → 告警上报 → 安全靠边/停车支持。
驻车与下电结束任务
保持驻车制动，完成状态存储与控制器休眠；活动：驻车保持 → 数据记录 → 下电时序 → 休眠/唤醒待命。

运行场景 正常 / 退化 / 异常

场景 O-1 高速领航跟车变道

智驾域输出目标车速与变道转向量，底盘协调电机驱动、转向与制动，在车流中平顺跟车并完成变道，保持车身稳定。

交互：智驾域（数据/信号）、轮胎路面（能量/活动）、仪表（状态反馈）
场景 O-2 城市拥堵跟停起步

低速工况下频繁加减速与停车，底盘保证起步平顺、跟停不溜车，制动与驱动衔接自然。

交互：驾驶员监控（活动）、BMS/动力域（能量）、轮速信号（信号）
场景 O-3 自动泊车入位

低速大转角反复转向，配合精确制动与低速驱动，完成泊车轨迹跟随与到位停车保持。

交互：智驾域（数据）、转向/制动执行器（活动）、驻车制动（能量保持）
场景 O-4 紧急主动制动/避障

触发主动安全时快速建立制动压力并结合转向稳定控制，降低碰撞风险或减轻碰撞后果。

交互：感知/安全系统（信号）、制动执行器（能量）、稳定性控制（活动）
场景 O-5 低附着路面行驶

湿滑/冰雪路面附着受限，底盘限制控制量，防止打滑与失控，维持方向可控与减速能力。

交互：轮速/附着估计（信号）、驱动防滑与稳定控制（活动）
场景 O-6 执行/电控通路失效（异常）

某控制器或执行通路失效时，系统检测并切换备份通路；若无法维持全功能，则进入受限降级并提示驾驶员，必要时支持安全停车。

交互：冗余控制器/备份执行器、仪表与车云告警（数据/活动）
异常场景只描述“可能出现的异常现象与应对活动”，不在概念阶段规定具体零部件失效机理；凡历史上出现过的异常，新系统概念文档中均需有对应分析与应对策略。

06

相关方需求条目

由相关方“需要”经分析、权衡后转化为可行、可验证的需求；优先级分为高 / 中 / 低，并标注需求依据。需求为相关方视角的高层需求，后续再向下派生系统（SRS）需求。

SR-01高对应：SH-01 用户 · SH-09 安全
线控底盘应能在正常与规定边界工况下，稳定完成转向、制动与驱动控制，保障车辆方向可控与减速能力。
行车安全是最高业务目标，用户与安全团队均要求系统不丧失基本可控性。
SR-02高对应：SH-03 智驾域
系统应提供标准化、时序明确的控制指令接收与状态反馈接口，支持智驾域下发纵向/横向目标并获取底盘执行状态。
智驾闭环依赖底盘可被算法控制，接口与时序不明确将导致闭环失效。
SR-03高对应：SH-09 安全 · SH-10 法规
关键转向/制动功能应具备冗余备份或失效降级路径，在主通路失效后维持基本可控，并触发分级告警。
法规与功能安全要求对单一失效进行防护，避免底盘功能完全丧失。
SR-04高对应：SH-01 用户
系统控制输出应平顺、线性，避免突兀加减速与急打方向；自动/手动切换过程应平滑、可感知。
用户满意度与乘坐舒适性要求控制动作连续自然，交接不产生抖动。
SR-05中对应：SH-01 用户 · SH-04 动力域
系统应结合路面附着与车辆状态协调驱动、制动与转向控制，防止打滑、失控，并合理利用能量回收。
低附着与极限工况下需在附着力范围内分配控制量，兼顾稳定与能效。
SR-06中对应：SH-06 测试 · SH-07 售后
系统应提供可观测的状态、故障码与诊断接口，支持下线检测、标定验证、售后维修与故障追溯。
测试与售后依赖数据定位问题；关键事件须可记录、可追溯以支持责任界定。
SR-07中对应：SH-07 售后 · SH-11 车云
系统应支持标定与软件版本的可管理升级，升级过程具备版本记录、回退与一致性校验能力。
平台化迭代与 OTA 要求版本可控，避免升级不一致或无法回退。
SR-08中对应：SH-10 法规 · SH-09 安全
系统应满足规定环境（温度、振动、电压、电磁兼容）下的工作要求，并在信息安全上具备访问控制与防护能力。
整车环境与网络安全准入是强制约束，需防止环境失效与非法访问/误控。
SR-09中对应：SH-02 整车厂 · SH-13 供应链
系统方案应在平台成本与进度约束内可行，关键件具备备选来源或风险预案，预留向架构演进的接口与算力空间。
采办方与供应链管理要求方案可落地、可量产，并适应长期架构演进。
SR-10低对应：SH-12 被影响方
系统应控制自身噪声、振动与对外排放影响，降低对周边交通参与者与环境的干扰。
被影响相关方要求系统在使用过程中不产生超出允许范围的外部负效应。
